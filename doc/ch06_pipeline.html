6.2. Надёжность доставки

Правило одно: каждый следующий хоп подтверждает приём, предыдущий только после этого удаляет. Бейдж хранит сегмент до ack шлюза (место позволяет держать недели); шлюз — до ack облака (7 дней буфера); в облаке сегмент немедленно попадает в S3, и только потом в очередь обработки. Все стадии идемпотентны по естественным ключам — повторная доставка/обработка безвредна, exactly-once достигается на уровне эффекта (upsert), а не транспорта. Ретраи с экспонентой и DLQ; застрявшее в DLQ видно на дашборде пайплайна. Потерять разговор можно единственным способом — физически утопить бейдж до контакта со шлюзом.

6.3. LLM-разбор: чем «структурированный разбор» является технически

Один вызов T-Pro 2.0 (32B, vLLM, guided JSON по схеме) на разговор: вход — транскрипт с ролями и confidence + профиль сделки из CRM (этап, модель, история) + методология продаж сети (конфигурируемый чек-лист этапов: контакт → выявление потребности → презентация → тест-драйв → работа с возражениями → деньги/трейд-ин/кредит → следующий шаг). Выход-схема (прил. В) написана так, чтобы каждый факт имел таймкод-якорь в транскрипте — РОП по клику слушает первоисточник, галлюцинации проверяемы за секунды. Второй, дешёвый проход (~8B или правила) — PII-маскирование транскрипта для долгого хранения и обучающих подборок (гл. 10). Промпт и схема версионируются; изменение — A/B на золотом наборе из 50 размеченных разговоров (создаётся на пилоте, гл. 11).

6.4. Сопоставление разговор ↔ сделка (вопрос 3 задания)

Три ступени, каждая закрывает свою долю случаев; цифры-цели по данным пилота:

  1. Контекст (авто, ~60–70%). Мы знаем менеджера (бейдж), время (запись) и площадку. В CRM у менеджера есть календарь визитов/тест-драйвов. Пересечение по времени однозначно → связка готова. Здесь окупается «свой CRM-модуль»: визиты — первоклассная сущность (гл. 7), и чем дисциплинированнее ведутся, тем выше автосопоставление — метрика этого тоже видна РОПу.
  2. Содержание (авто, +15–20%). LLM извлекает из транскрипта имя клиента, телефон (клиент диктует при записи на тест-драйв), модель, трейд-ин → fuzzy-поиск по клиентам/сделкам менеджера и площадки за ±30 дней. Порог уверенности консервативный: ложная связка вреднее несвязанного разговора.
  3. Подтверждение (менеджер, 1 минута в день). В конце смены Telegram-бот показывает 5–8 карточек: «15:20–15:55, обсуждали X5 в trade-in — это Иванов И.? [Да] [Выбрать] [Новый клиент]». «Да» — один тап; «Новый клиент» — автосоздание лида с предзаполнением из транскрипта (имя, телефон, интерес) — менеджеру это экономит ручной ввод, поэтому шаг воспринимается как польза, а не контроль. Неподтверждённое остаётся в очереди РОПа.

Все связки логируются с источником и уверенностью; ошибочную РОП/менеджер разрывают в один клик, разрыв — обучающий сигнал для порогов матчинга.

6.5. SLA этапа 1

Разговор, закончившийся до 16:00, — карточка в CRM в тот же день; вечерние — к 9:00 следующего дня. Основная задержка — не вычисления (пиковый час 100 менеджеров парк разбирает за ≤2 ч, гл. 8), а доставка хвостов записи при слабом аплинке; поэтому шлюз выгружает сегменты с приоритетом «сегодняшнее раньше вчерашнего», а бейджи начинают выгрузку оппортунистически в течение дня, не дожидаясь дока.
