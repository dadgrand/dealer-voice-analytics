# Скелет документа (план глав)

Целевой объём: 25–35 стр. Язык: русский. Тон: инженерный, решения с обоснованием,
альтернативы показаны и отвергнуты аргументированно. Все цены — с источниками и датой.

## 0. Титул + Executive summary (1 стр.)
- Решение в трёх абзацах: носимый бейдж → своя сеть на площадке → батч-разбор в РФ-облаке → CRM.
- Ключевые цифры: CAPEX $/менеджера, OPEX $/менеджера/мес при 100 и 1000, латентность подсказки этапа 2.
- Почему полезно: 1 абзац ROI.

## 1. Постановка задачи и допущения (1.5 стр.)
- Пересказ требований своими словами + модель нагрузки (таблица: разговоры/смена, минуты, часы аудио).
- Явные допущения (график работы, пиковый профиль субботы, 22 смены/мес).
- Вопросы заказчику (задание поощряет): график смен, текучка, доля разговоров вне шоурума
  (тест-драйв!), политика ретенции, СБ-требования, есть ли DECT/радиосвязь на площадках.

## 2. Ключевые решения — обзор (2 стр.)
- Таблица «решение → альтернативы → почему так». 6 решений:
  1) захват: носимый бейдж (vs потолочные массивы, vs смартфон, vs готовый диктофон);
  2) сеть: своя AP + LTE, независимость от Wi-Fi дилера;
  3) разделение голосов: асимметрия каналов бейджа + диаризация, а не blind diarization;
  4) обработка: батч в облаке РФ (152-ФЗ), self-hosted ASR/LLM на выделенных GPU;
  5) CRM: свой модуль (у заказчика самописная CRM → проектируем контракт и модель данных);
  6) UX менеджера: ноль кнопок, док-станция, подтверждение сделок одним тапом.
- Диаграмма: общая архитектура (уровень 1).

## 3. Хардвер (ГЛАВНАЯ глава, 6–8 стр.) — «Важно!!!»
### 3.1 Бейдж-рекордер
- Блок-схема компонентов (диаграмма): ESP32-S3 + 2× MEMS (ICS-43434) + microSD + LiPo +
  BQ24074 + MAX17048 + USB-C + пого-пины + RGB LED.
- Таблица BOM с ценами qty 100 / qty 1000, партномера.
- Акустика: почему 2 микрофона (вертикальная пара: рот менеджера сверху/фронт, клиент+зал),
  SNR/AOP выбор, ветрозащита, крепление (клипса/шнурок, ориентация).
- Питание: бюджет мощности по режимам (запись на SD / запись+Wi-Fi burst),
  расчёт батареи на 11-часовую смену с деградацией до 80% за 2 года.
- Прошивка: RTOS-задачи, кольцевой буфер, Opus 16 кГц mono на борту (или ADPCM+транскод
  на шлюзе — решить по данным исследования), шифрование сегментов, ротация ключей,
  OTA. Хранение до 3 смен при недоступности сети.
- Жизненный цикл: провижининг (QR + серийник), привязка к менеджеру через док,
  индикация (1 RGB: зелёный пишет / синий выгружает / красный проблема), ЗИП 10%.
- Себестоимость итог: $X при 100, $Y при 1000. Сравнение с готовыми (Plaud NotePin и
  OEM-бейджи) и почему своё (цена при тираже, контроль прошивки, пого-док, шифрование).
### 3.2 Док-станция
- Мульти-док на 10 мест: пого-зарядка + опционально USB-выгрузка как fallback; BOM.
### 3.3 Площадочный шлюз
- Мини-ПК N100 + своя Wi-Fi AP (отдельный SSID/VLAN) + LTE-роутер с M2M SIM.
- Роль: приём сегментов, буфер 7 дней, транскод/предобработка, mTLS-туннель в облако,
  локальный NTP, fleet-агент. Диаграмма площадки.
- CAPEX площадки и на менеджера. Итог: укладываемся в $100.

## 4. Аудиотракт и разделение голосов (2.5 стр.)
- Почему близкий микрофон решает шум (расстояние рот-микрофон 15–25 см vs 2–4 м у потолочных).
- Двухступенчатая диаризация: (а) энергетическая/спектральная асимметрия каналов бейджа —
  менеджер всегда «ближний», (б) pyannote/эмбеддинги только для «дальней» речи
  (клиент vs соседний разговор vs второй клиент). Обработка перекрытий.
- Сегментация непрерывной смены на разговоры: VAD (Silero) + паузы + смена собеседника +
  геометрия (RSSI ближайших доков/маяков — опционально) → «кандидаты разговоров».
- Качество: ожидаемый WER в шуме, деградационные режимы, что делаем с «мусорными» кусками.

## 5. Облачная архитектура и стек (3 стр.)
- Диаграмма: ingest (mTLS) → S3-совместимое хранилище → очередь → воркеры
  (VAD/диар/ASR/LLM) → PostgreSQL → API → CRM-модуль/дашборд; всё в РФ-облаке.
- Выбор стека с обоснованием: Go/Python сервисы, PostgreSQL, S3, NATS/Kafka (выбрать),
  ClickHouse для аналитики (или отложить), Kubernetes vs simple VMs — по масштабу.
- ASR: GigaAM-2 vs Whisper large-v3 (по данным исследования) на выделенных GPU;
  LLM: self-hosted Qwen (ночной батч на тех же GPU) vs GigaChat API — расчёт обоих.
- Мониторинг: флот устройств (последняя выгрузка, батарея, % записанных смен),
  пайплайн (лаг очереди), качество (WER-прокси, доля несопоставленных разговоров).

## 6. Пайплайн данных: от микрофона до CRM (3 стр.)
- Sequence-диаграмма с таймингами каждого шага (запись → сегмент 5 мин → выгрузка →
  сборка разговора → диар → ASR → LLM-разбор → сопоставление → карточка в CRM).
- Формат данных на каждом шаге (сегмент Opus + метаданные; транскрипт JSONL с ролями;
  разбор JSON по схеме: этапы, возражения, обязательства, чек-лист, оценки).
- Идемпотентность, ретраи, exactly-once на уровне разговора.
- SLA этапа 1: разбор в CRM ≤ N часов после разговора (посчитать от очереди).

## 7. Свой CRM-модуль и сопоставление разговор↔сделка (2.5 стр.)
- Модель данных (ER-диаграмма компактная): Manager, Badge, Site, Client, Deal, Visit,
  Conversation, Transcript, Analysis, CoachingTask.
- Трёхступенчатое сопоставление: (1) менеджер+время+календарь визитов; (2) сущности из
  транскрипта (имя, телефон, модель, trade-in) → fuzzy-match; (3) однотаповое подтверждение
  менеджером в конце смены (список из 5–8 карточек). Автосоздание лида при отсутствии.
  Confidence-скоринг, ручная очередь РОПа для низкой уверенности.
- Дашборд РОПа: воронка по этапам, необработанные возражения, рейтинг, динамика; карточка
  разговора с плеером и переходами по транскрипту.
- API-контракт (таблица эндпоинтов) — раз CRM самописная, задаём контракт сами.

## 8. Расчёты (3 стр.) — «вопрос 2 задания»
- Поток аудио в пиковый час (100/1000): одновременные разговоры, Мбит/с, ГБ.
- Параллельные обработчики: GPU-часы/сутки, число GPU, стратегия (выделенные + автоскейл).
- Хранение: ГБ/мес, steady-state при ретенции 6 мес, ₽.
- Таблица OPEX на 100 и 1000: GPU, LLM, хранение, бэкенд, LTE → $/менеджера/мес vs $15.
- Таблица CAPEX: бейдж, док, шлюз → $/менеджера vs $100.
- Чувствительность: пессимист/оптимист (RTFx, доля речи, цены GPU).

## 9. Этап 2: подсказки в реальном времени (3 стр.)
- Что меняется: бейдж начинает стримить (Opus 20 мс кадры) через свою AP на шлюз.
- Бюджет задержки по звеньям (диаграмма-таймлайн): захват+кадрирование → сеть → стриминг-ASR
  (partial) → триггеры (правила <50 мс на шлюзе) + LLM-подсказка → доставка.
  Целевые числа из бенчмарков исследования; итог ~1.5–3 с.
- Куда доставлять: часы (вибро+короткий текст) vs телефон vs наушник — сравнение, выбор.
- Деградация: нет LTE/интернета → подсказки локальными правилами на шлюзе (без LLM);
  нет и шлюза → просто пишем, подсказок нет. Этап 1 не страдает.
- Изменения в облаке: streaming ASR пул «горячих» GPU по пиковому часу (расчёт числа).
- Честная секция: что НЕ обещаем (полный суфлёр), почему подсказка = короткий nudge.

## 10. Надёжность, безопасность, приватность (2.5 стр.)
- Отказы: таблица «что ломается → что происходит → что теряем» (Wi-Fi, LTE, шлюз, док,
  бейдж утоплен, облако лежит). Ключевой принцип: запись локально переживает всё.
- Безопасность: шифрование на SD (ключ на выгрузку), mTLS device identity, подписанные OTA,
  RBAC в CRM, аудит доступа к записям, PII-маскирование в транскриптах для обучения.
- Юридика (по данным исследования): 152-ФЗ, голос ≠ биометрия при нашем использовании,
  основания обработки, таблички+скрипт уведомления, ЛНА для сотрудников, локализация в РФ,
  ретенция и обезличивание. Чек-лист внедрения.

## 11. Внедрение и анти-саботаж (1.5 стр.)
- Пилот: 1 площадка, 5 менеджеров, 6 недель; метрики выхода (≥80% смен записано,
  ≥70% разговоров сопоставлено автоматически, РОП использует дашборд еженедельно).
- Анти-саботаж: ноль действий для записи; док = зарядка (забыть нельзя); подтверждение
  сделок = 1 минута в Telegram; политика «записи для обучения, не для наказаний» (без этого
  менеджеры будут «забывать» бейджи); геймификация аккуратно.
- Роллаут волнами, обучение РОПов, поддержка/RMA-процесс.

## 12. Почему это будет полезно: ROI (1 стр.)
- Модель: средний дилер 100 сделок/мес на площадку, конверсия шоурум→сделка ~15–25%;
  +1–2 п.п. конверсии от работы с возражениями = +N машин/мес; маржа $X/машина.
  OPEX системы на площадку $Y/мес → окупаемость.
- Нефинансовые: onboarding новичков быстрее, единая методология продаж, данные для
  маркетинга (что спрашивают клиенты).
